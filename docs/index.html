Building an authenticated callout from Salesforce to a Lambda function

Every box left of API Gateway lives in Salesforce; everything from API Gateway onward lives in AWS. The two platforms never share a login — they share one secret value, injected as a header.

02

AWS side

Lambda function

ComputeComplete

Serverless function — code that runs on demand with no server to provision or patch. It only runs (and only costs anything) when invoked.

name sfdc-hello-lambda
runtime Python 3.12
region us-east-1
Why it mattersThis is the actual endpoint of "AWS processing" — the piece Salesforce is ultimately trying to reach. Everything else in this diagram exists to get a request to this function safely.

API Gateway

Front doorComplete

The managed HTTPS entry point that sits in front of Lambda. Lambda itself has no public URL of its own — API Gateway is what makes it callable over the internet.

api FirstAWSAPI (HTTP API)
id ‹redacted›
route GET /hello
Why it mattersHTTP API (not the older REST API type) was chosen — cheaper and lower-latency for a simple pass-through route like this. Its invoke URL is exactly what gets registered as the Named Credential's endpoint on the Salesforce side.

Secrets Manager

Credential storeComplete

Encrypted, managed storage for the API key, so it never sits in plaintext inside the Lambda's source code or environment variables.

secret sfdc/lambda/apikey
key x-api-key
Why it mattersLambda reads the current key at invocation time instead of trusting a value baked into deployed code. The key can be rotated in Secrets Manager without touching or redeploying the function.

IAM inline policy

Least privilegeComplete

A permission attached directly to the Lambda's execution role, scoped to exactly one action on exactly one resource.

name ReadLambdaAPIKey
grants secretsmanager:GetSecretValue
scope sfdc/lambda/apikey only
Why it mattersThe function can read its own secret and nothing else in the AWS account. If the function were ever compromised, the blast radius is one secret, not the whole Secrets Manager store.
03

Salesforce side

External Credential

Auth definitionComplete

Defines how to authenticate, kept separate from where to call. This is the current recommended pattern — it replaced folding auth details directly into a legacy Named Credential, and was used here instead of a Connected App because there's no OAuth flow: just one static header.

name AWS Lambda Credential
scheme Custom
principal type Named Principal
Why it mattersCustom auth lets Salesforce attach an arbitrary header (x-api-key) to every callout — there's no built-in scheme for "static API key in a custom header," so Custom is what makes this possible at all.

Principal

Secret holderComplete

The actual credential value lives here, one level under the External Credential. "Named" means it's a single org-wide credential, not one per user.

name AWSlambdaPrincipal
header x-api-key
Why it mattersStoring the key here — rather than in Apex — means the secret never appears in code, debug logs, or version control. Apex only ever references the Named Credential by name.

Named Credential

EndpointComplete

Points at the actual URL to call and links back to the External Credential for how to authenticate the call.

name AWS_Lambda_Hello
url API Gateway invoke URL
auth AWS Lambda Credential
Why it mattersApex calls callout:AWS_Lambda_Hello instead of a hardcoded URL. No Remote Site Settings needed, and the endpoint can move without a code change or deployment.

Apex + Permission Set

Access controlComplete

AWSLambdaService.callHelloLambda(String name) builds the HttpRequest against the named credential. The AWS Integration permission set separately grants External Credential Principal Access.

class AWSLambdaService
perm set AWS Integration
Why it mattersCode deployment and credential access are two separate gates. A user can have the Apex class available to them and still be unable to actually use the stored secret without this permission set.
04

What happens on one request

  1. Apex issues the callout
    Code calls callout:AWS_Lambda_Hello/hello — no URL or secret appears in the class itself.
  2. Salesforce resolves credentials
    The platform looks up the Named Credential, follows it to the External Credential, and attaches the Principal's x-api-key header automatically.
  3. Request leaves Salesforce
    An HTTPS request hits the API Gateway invoke URL for GET /hello.
  4. API Gateway routes to Lambda
    The matching route forwards the request, headers included, to sfdc-hello-lambda.
  5. Lambda fetches the real secret
    Using its IAM-granted permission, the function calls Secrets Manager for the current value of sfdc/lambda/apikey.
  6. Lambda validates the header
    The incoming x-api-key is compared against the Secrets Manager value. Mismatch → reject before any business logic runs.
  7. Response returns to Apex
    Lambda's response travels back through API Gateway; Apex reads it off the HttpResponse.
05

Quick reference

TermWhat it actually means here
External CredentialModern, reusable definition of an auth scheme — decoupled from any one endpoint, so it can back multiple Named Credentials at once.
Named CredentialEndpoint + a pointer to the auth scheme that secures it. What Apex actually calls.
Connected AppNot used here — that's for OAuth-based flows (login, or Salesforce as the OAuth server/client). This integration uses a static header instead.
HTTP API vs REST APIBoth are API Gateway product types. HTTP API is the newer, cheaper, lower-latency option for straightforward request pass-through — used here.
IAM inline policyA permission attached directly to one role rather than a standalone reusable policy — appropriate for a one-off, tightly scoped grant like this.
Secrets ManagerEncrypted secret storage with an API to fetch values at runtime, instead of hardcoding them.
